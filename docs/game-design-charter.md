## 1. 核心游戏思路（一句话）

> **让每个人都能轻松放技能的格斗游戏：招式多、量大管饱、无搓招门槛；
> 策略深度来自「用自己的一整套招式，去反制对方可能放出的各种技能」。**

展开成三句：

| 原则 | 含义 | 由此产生的设计要求 |
| --- | --- | --- |
| **人人能放** | 不需要搓招（236/623/214…）。所有技能都是「方向 + 按钮」或「按钮 + 按钮」 | 输入层禁止出现需要精准输入的指令；一个新手按一次就能放出大部分技能 |
| **量大管饱** | 每个角色的技能数量要多（普通技 12 个起、大型技能 8 个以上） | 角色表按"技能条数"而非"连段深度"来扩张；美术产能优先供给动作种类 |
| **反制为纲** | 深度不来自搓招博弈，而来自**识别当前情境**并用合适的招式应对 | 招式之间必须有**可辨识的情境属性**（快/慢、飞行/跳跃、上/中/下、距离），且这些属性要能被玩家记住（**注意：这是「属性」不是「关系矩阵」，见 §3.1**） |

**这与传统格斗游戏的差别**：传统格斗的深度来自"把三个指令打成一套连招"；
本作的深度来自"情境识别 + 空间博弈"（见 §3 的三层模型）。
因此：

- 我们的**取消/连段系统不是卖点**（但仍需存在，用于正常攻防）
- 我们的**单招设计质量与相性矩阵**才是核心资产
- 平衡的目标不是"谁的真确更高"，而是"谁的招式组合更难被针对"

## 2. 操作体系（2026-10-02 定版）

### 2.1 键位分工

| 键 | 角色 | 耗气 | 用途 |
| --- | --- | --- | --- |
| `A` | 轻拳 | ❌ | 普通招式第一档（站/蹲/空） |
| `S` | 重拳 | ❌ | 普通招式第二档 |
| `Z` | 轻脚 | ❌ | 普通招式第三档 |
| `X` | 重脚 | ❌ | 普通招式第四档 |
| `C` | **气键** | ✅ | 与方向或 A/S/Z/X 组合 → 中型技能 |
| `D` | **超气键** | ✅ | 与方向或 A/S/Z/X 组合 → 大型技能；`C+D` 同按 → 终极技 |
| `方向键` | 修饰 | — | `↓` 蹲、`↑` 跳、`→` 前、`←` 后（**不做 236/623 这类序列**） |
| `Enter` | — | — | START / 确认 |

**规则一句话**：

```text
只用 A/S/Z/X        → 不耗气的普通招式
带 C 或 D           → 消耗气的技能
```

这条规则本身就是教学成本的上限：**玩家学会一次，之后不需要再记指令表**。

### 2.2 为什么这么设计

1. **C/D 之前是空闲键**（引擎的 `c` / `z` 按钮在我们的四键体系里没有用途），
   不需要新增按键，也不需要改引擎键位。
2. **"带不带 C/D"是一个可以用肌肉记忆表达的判断**（我这一下要不要放气），
   比"搓什么招"快一个数量级。
3. **它天然分层**：普通招式负责日常攻防与消耗，气键负责破局与终结，
   玩家可以按"我现在要不要花气"来选择动作。

### 2.3 输入形态清单（全部为简单组合）

| 形态 | 示例 | 归类 |
| --- | --- | --- |
| 单键 | `A` | 普通（站姿第一档） |
| 方向 + 单键 | `↓A` / `→A` / `←S` | 普通（蹲/前/后变体） |
| 空中 + 单键 | 空中 `S` | 普通（跳跃攻击） |
| 气键 + 方向 | `↓C` / `→C` / `←D` | 中/大型技能 |
| 气键 + 普通键 | `C+A` / `D+S` | 中/大型技能 |
| 双气键 | `C+D` | 终极技（耗满气） |
| 方向 + 投技键 | `→A`（贴身） | 投技 |

**明确禁止**：任何形如 `↓↘→+A` 的序列指令；任何需要摇杆/搓键的输入。

## 3. 深度模型（三层结构）

> 本节在 2026-10-02 做过一次修订。原因是发现「深度只靠相性读招」有一个结构性缺陷：
> **相性深度是易变的**——它依赖玩家记住并预测对手的行为，一旦不知道对方会怎么打，
> 深度就归零；而执行深度是**可靠**的，练会了每次都能用。修订后深度由三层承载。

```text
┌─────────────────────────────────────────────┐
│ ① 广度层：招式多，每招占一个「情境位」        │  ← 你的原始提案，保留
├─────────────────────────────────────────────┤
│ ② 空间与惩罚层：距离 / 空挥 / 确反 / 帧数据 │  ← 引擎免费提供（我们已有）
├─────────────────────────────────────────────┤
│ ③ 可选技术层：同键二次 / 方向变体等          │  ← 不设门槛，只给愿意深挖的人
└─────────────────────────────────────────────┘
```

### 3.1 ① 广度层：把「相性关系」改成「情境属性」

关键修订：**不要设计"A 克 B"的关系矩阵，而是给每招打属性标签**。

| 维度 | 取值 |
| --- | --- |
| 距离 | 近 / 中 / 远 |
| 高度 | 上段 / 中段 / 下段 |
| 速度 | 快（≤4 帧起手）/ 慢 |
| 飞行 | 是 / 否 |
| 破防 | 是 / 否 |
| 部位 | 头 / 胸 / 脚 |

这样做的三个好处：

1. **学习成本从「背表」降到「认情境」**——玩家判断的是"现在是什么情况"，
   而不是"他会放什么克制我"。
2. **平衡成本从 O(n²) 降到 O(n)**——平衡检查变成"每个情境是否有人覆盖/克制"，
   可枚举、可自动化（呼应 P10 的自动化平衡）。
3. **「量大管饱」有了客观判据**——不是"有 20 招"，而是
   **「我的招式集覆盖了所有情境吗」**。这直接堵住"凑数招"。

### 3.2 ② 空间与惩罚层（我们最被低估的资产）

这一层**不依赖对手怎么想**，只依赖你自己和帧数据，所以深度**不会随对手变化而蒸发**。
而它需要的东西我们**在 P1–P5 已经验证过了**：帧数据、推挤盒、飞行道具、硬直约定。

具体手段：空挥惩罚、距离控制、确反（punish）、防御与破防博弈。
Nidhogg / Divekick 那类游戏的深度主要就在这里，而不在招式表。

### 3.3 ③ 可选技术层（把执行层降级，而不是删除）

**不设门槛、只作为可选挑战**。数量要少而准，每个角色 3~5 个，绑在高辨识度动作上：

- 同键二次 = 强化版（更高伤害/不同判定）
- 完美防御窗口 = 反弹
- 特定招式的前摇取消 = 反击

**不要通用化**——一旦变成"所有招都能取消"，它就又变成记忆负担了。

### 3.4 输入层可以更语义化（不增加任何按键）

在「带 C/D = 耗气」之上，**用方向表达意图**：

```text
← + 气键   = 想拉开距离的技能（后撤斩 / 后跳射）
→ + 气键   = 想突进的技能（突进斩 / 前冲）
↓ + 气键   = 想压制的技能（下段 / 破防）
```

玩家按方向就表明了"我现在要干什么"，技能选择变成"在这个意图下选哪一招"。
决策更清晰，**按键一个都不加**。

### 3.5 对 AI 的影响（P8/P9 的方向要跟着改）

原提案下 AI 会去做"预测对手要放什么"——在 20 招的空间里猜，AI 会变成不可战胜的读心者。
新模型下 AI 应当去做 **「制造情境」**：通过移动和出招，逼迫对手进入对自己有利的局面。

这更可实现（AI 不需要知道你在想什么，只需要算位置关系与帧优势），
而且**与方向一致**——AI 同样受益于简单输入。

### 3.6 平衡检查表（每个角色每版都过一遍）

- [ ] 每个情境（距离 × 高度 × 速度）是否**至少有一招覆盖**？
- [ ] 是否存在"无人克制"的情境（= 无解）？
- [ ] 是否存在"人人都有解"的情境（= 无深度）？
- [ ] 每个气键技能是否都有**至少一个普通招式能先手压制**它？
- [ ] 终极技的出手机会是否被"防/破"类技能覆盖？
- [ ] AI 是否会**制造情境**，而不是只读招？

### 3.7 已知风险（有意保留，不是遗漏）

| 风险 | 现状判断 | 对策 |
| --- | --- | --- |
| **动画产能** | ⚠️ **最大风险**。20+ 招 = 20+ 段**动画**（不是 20 张图）。AI 重绘能解决静态图，做连贯动画更难 | 换动作更全的素材源；`anim_strip` + AI 辅助重绘；招式复用。**P7 开工前必须有结论** |
| **决策量过大** | ⚠️ 选项一多就奖励快速反应，可能筛掉"想不清楚的人" | 每招使用情境收窄；靠 ② 空间层降低思考负担 |
| **角色同质化** | ⚠️ 简单输入 + 招式多，容易变成"招式清单" | 角色个性靠**机制差异**（Archer 的双刀 / 弓 / 无限剑制是三条线） |
| 相性退化成"查表" | ✅ 已缓解 | 3.1 的属性化 + 3.2 的空间层 |

## 4. 角色内容产能（服务"量大管饱"）

一个角色的最低内容量：

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 普通招式 | **12**（站/蹲/空 × A/S/Z/X） | 基础，状态机固定 |
| 方向变体 | 4~8 | 前后方向带来的位移/性质变化 |
| 中型技能（`C` 系） | 4~6 | 耗气 300~600 |
| 大型技能（`D` 系） | 4~6 | 耗气 800~1200 |
| 终极技（`C+D`） | 1~2 | 耗满气 |
| 投技 | 2 | 前后各一 |

**美术成本是瓶颈**：每多一个技能就多一组动画。因此产能提升的优先级是：

1. **换更高精度、动作更全的美术源**（进行中，见 P6）
2. **动作条工具 + AI 辅助重绘**（`tools/anim_strip.py` 已在用）
3. 招式复用：同一套动画可服务不同技能（不同判定/不同消耗）

## 5. 技术方向（不变的部分）

战略转向**不改引擎、不改架构**：

- 引擎仍是 IKEMEN GO `v1.0.0-rc.5`（不重造）
- 角色仍是"骨架 + 美术 + 映射表"三层分离（`archer.sff` / `.air` / `asset_map.csv`）
- 工具链仍为只读 + 可复现（`tools/sffctl` `airtool` `sndctl` `sffpack` `validate_character`）
- **变的是**输入层（去掉搓招）与内容层（招式数量与相性）

**输入层改造工作量预估**：现有 `command.zss` 已是"命令名 → 状态号"的路由层，
把 MUGEN 的 `QCF_x` 之类换成 `SIMPLE_*` 形式的简单组合是**改命令定义 + 改路由顺序**，
不动状态机。预计每个角色半天。

## 7. 不变的东西（提醒别过度改动）

- 非商用同人素材的合规处理（见 `assets/LICENSE_MANIFEST.csv`）
- 美术终将用 AI 重绘：因此**素材精度优先、动画数量优先**，不要过早手工优化
- 一切变更都要有实测证据（工具 + 截图 + 状态读数）
- `game/` 是 Git 真值，`engine/ikemen-go/` 只作为运行时副本
