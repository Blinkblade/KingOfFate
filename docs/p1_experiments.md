## 1. 实验方法：怎么"看见"引擎内部

IKEMEN 不带日志式的角色状态输出。要验证"改了 X 会导致 Y"，必须先把**可观测性**建起来。

### 1.1 观测装置（三段）

```text
① 无人值守启动一局        tests/p1/capture_match.ps1
     └─ 启动 Ikemen_GO.exe，指定 -p1/-p2/-s/-windowed/-nosound/-time
     └─ 获取前台焦点（AttachThreadInput + SetForegroundWindow，并回读验证）

② 打开引擎自带的调试覆盖层  Ctrl+C → 判定框   Ctrl+D → 状态读数
     └─ F1–F10 / SPACE / PAUSE / SCROLLLOCK 被引擎占用，不可用

③ 注入输入 + 抓帧          keybd_event 持续按住；按固定间隔 burst 抓图
     └─ 输出：logs/p1/shots/*.png（截图）+ *_report.txt（运行报告）

④ 把读数拼成可读证据        tests/p1/montage_states.ps1
     └─ 裁出每帧左下角的状态文本条带，纵向堆叠成 montage_*.png
```

### 1.2 `Ctrl+D` 覆盖层能读出什么

这是 P1 全部量化结论的来源。逐帧打印四行（出处：`engine/ikemen-go/external/script/debug.lua`）：

```text
P1: 56; LIF:1000; POW: 0; ATK: 100; DEF: 100; RED:1000; GRD:1000; STN:1000
P2: 57; LIF:1000; POW: 0; ATK: 100; DEF: 100; RED:1000; GRD:1000; STN:1000
ActionID: 0 (P1); SPR: 0,0; ElemNo: 1/11; Time: 3/10 (4/151)
State No: 0 (P1); CTRL: 1; Type: S; MoveType: I; Physics: S; Time: 10
```

| 字段 | 含义 | 用在哪 |
| --- | --- | --- |
| `LIF` | 体力（1000 起） | **E2** 伤害、**E5/E6** 命中与否 |
| `POW` | 气槽 | E2（附带发现）、E6（空挥集气） |
| `RED` | 可回复体力池（红血） | E2（附带发现） |
| `ActionID` | **当前动画号**（= `anim: N`） | E3、E4 |
| `ElemNo: a/b` | 当前动画元素 / 元素总数 | **E3** |
| `Time: t/T (g/G)` | 元素内已过帧 / 元素总帧；(动画累计帧 / 动画总时长) | **E3** 的核心 |
| `State No` | 当前状态号 | **E2–E6 全部** |
| `Type` / `MoveType` / `Physics` | 状态头三个属性 | E1–E6 |
| `CTRL` | 是否可操作 | E2–E6 |

**为什么用"裁条带拼图"而不是自动读文字**：GDI+ 逐像素比较在多帧间不可靠
（`LockBits` 裁剪会返回整图 stride），曾导致误判。裁条带 + 人工判读虽然"土"，
但**证据是图像本身，不可能读错**，且可以直接附在 PR 里被人复核。

## 2. 前置实验 E0 — 建立可用的按键注入通道

**这是一个意外的、但必须先解决的问题。** 没有可靠的输入通道，后面 6 个实验全都做不了。

### 2.1 问题

`capture_match.ps1` 用 `keybd_event` 合成按键。但引擎只认其中一部分。

### 2.2 探测过程与结果

在 `save/config.ini` 里临时把各按钮绑到待测虚拟键，逐个 hold 并读状态：

| 虚拟键 | 键名 | 引擎是否接收 | 证据 |
| --- | --- | --- | --- |
| `0x09` | TAB | **是** | `montage_probe1.png` |
| `0x0D` | RETURN | **是** | `montage_probe1.png` |
| `0x2D` | INSERT | 否 | `montage_probe1.png` |
| `0x2E` | DELETE | 否 | `montage_probe1.png` |
| `0x24` | HOME | 否 | `montage_probe1.png` |
| `0x23` | END | 否 | `montage_probe1.png` |
| `0x21` | PAGE UP | 否 | `montage_probe1.png` |
| `0x4A` | J | 否 | `montage_probe1.png` |
| 字母 a / s / z | — | 否 | `diagA/diagC/diagD/diagF*` 系列 |
| `0xBC` | COMMA | 否 | `e5_A_comma_*` |

### 2.3 结论与取舍

- **可用的注入通道只有 TAB（→ button `x`）与 RETURN（→ button `y`）。**
- 因此 E1–E6 的运行时键位被锁定为：

  ```ini
  ; engine/ikemen-go/save/config.ini（运行时，gitignored）
  x = TAB
  y = RETURN
  ```

- 实验全部结束后，该文件**已从备份还原**为原始键位。
- 另发现：`F1`–`F10`、`SPACE`、`PAUSE`、`SCROLLLOCK` 已被引擎占用，不可用作探测键。

> **复现性注记**：E1–E6 依赖上面这个运行时的键位设置。
> `save/config.ini` 是 gitignored 的运行时文件，不在仓库里；
> 复现时需自行把 `x`/`y` 绑到任意"合成输入可达"的键上（本机是 TAB/RETURN）。
> 这是本实验装置的一个真实约束，不是被隐藏的前提。

## 3. E1 — 角色常量（`.const`）是否真的控制移动

| 项 | 内容 |
| --- | --- |
| **修改前** | `walk.fwd = 2.4` |
| **修改文件** | `game/chars/p1_kfm_zss_lab/kfm.const` |
| **修改位置** | 第 55 行，`[Velocity]` 段 |
| **修改内容** | `walk.fwd  = 2.4` → `walk.fwd  = 12.0` |
| **预期** | 前进速度变为约 5 倍；同样按住时长走过更远的距离 |
| **运行方式** | `capture_match.ps1 -p1 p1_kfm_zss_lab -p2 kfm_zss -s stage0 -windowed -nosound -time 45`；hold `0x27`（→ 前进方向）0.35 s，各抓一张图 |

### 实际结果

| | 基线（2.4） | 改动后（12.0） |
| --- | --- | --- |
| 角色脚下位置读数 | `KFM P1 Lab, 1, 56` | `KFM P1 Lab, 1, 9…`（被对手标签遮挡末位） |
| 角色屏幕位置 | 屏幕左侧 | **已冲到对手身前，两人重叠** |
| 对手位置 | `Kung Fu Man, 2, 57` | `Kung Fu Man, 2, 57`（未动，对照组） |

证据：[`e1_base_walk_full.png`](evidence/p1/e1_base_walk_full.png) /
[`e1_mod_walk_full.png`](evidence/p1/e1_mod_walk_full.png) /
[`e1_base_walk_nametag.png`](evidence/p1/e1_base_walk_nametag.png) /
[`e1_mod_walk_nametag.png`](evidence/p1/e1_mod_walk_nametag.png)

### 结论

**`[Velocity] walk.fwd` 就是"每 tick 的 x 位移量"。**

定量核对：hold 窗口 0.35 s @ 60 fps ≈ 21 tick；`21 × 2.4 = 50.4`，
实测基线位移读数 ≈ 56，**数量级与量纲都对得上**。
改动后同样 0.35 s 内角色已走完全程并贴住对手，位移被**推挤盒（push box）截断**。

> **证据强度说明（诚实标注）**：本实验证明了"常量语义正确、改它确实生效"，
> 但**没有**直接读出 5× 的倍率——原因是舞台宽度不足以让高速角色自由跑满，
> 角色撞上对手后被挡住。要直接读出倍率，正确做法是测 **time-to-contact**
> （改变速度后，从开局到贴住对手所需的时间之比）。这一项留给 P2 用
> `displayToClipboard` 输出 `pos x` 后补做。

## 4. E2 — 招式伤害（`hitDef.damage`）是否就是掉血量

| 项 | 内容 |
| --- | --- |
| **修改前** | `damage: 23, 0` |
| **修改文件** | `game/chars/p1_kfm_zss_lab/kfm.zss` |
| **修改位置** | 第 229 行，`[StateDef 200]`（站立轻拳）的 `hitDef{}` 内 |
| **修改内容** | `damage: 23, 0;` → `damage: 137, 0;` |
| **预期** | 命中一次，对手体力分别下降 23 / 137 |
| **运行方式** | 同一命令 + hold `0x09`（→ `x` 键）0.45 s，burst 抓 14 帧 |

### 实际结果

**基线（damage = 23）** —— 见 [`montage_e2_base.png`](evidence/p1/montage_e2_base.png)：

| burst | P1 State | P1 POW | P2 LIF | P2 POW | P2 RED |
| --- | --- | --- | --- | --- | --- |
| #01（出招前） | 0 | 0 | **1000** | 0 | 1000 |
| #02 | 200 (Time 1) | 10 | 1000 | 0 | 1000 |
| #03 | 200 (Time 3) | 10 | 1000 | 0 | 1000 |
| **#04（命中）** | 200 (Time 3) | **26** | **977** | **13** | **983** |
| #05–#11 | 200 | 26 | 977 | 13 | 983 |
| #12–#14 | 0（回到待机） | 26 | 977 | 13 | 983 |

**ΔLIF = 1000 − 977 = 23** ✅ 精确等于 `damage`。

**改动后（damage = 137）** —— 见 [`montage_e2_mod.png`](evidence/p1/montage_e2_mod.png)：

| burst | P1 State | P1 POW | P2 LIF | P2 POW | P2 RED |
| --- | --- | --- | --- | --- | --- |
| #01（出招前） | 0 | 0 | **1000** | 0 | 1000 |
| **#04（命中）** | 200 (Time 3) | **105** | **863** | **82** | **898** |
| #05–#11 | 200 | 105 | 863 | 82 | 898 |

**ΔLIF = 1000 − 863 = 137** ✅ 精确等于 `damage`。

### 附带发现（同一实验顺带得到）

| 量 | damage 23 | damage 137 | 结论 |
| --- | --- | --- | --- |
| 攻击方 P1 集气 | 10 → **26** | 10 → **105** | **伤害越高，攻击方集气越多** |
| 防守方 P2 集气 | 0 → **13** | 0 → **82** | **伤害越高，被打方集气也越多** |
| P2 红血池 `RED` | 1000 → **983**（Δ17） | 1000 → **898**（Δ102） | `RED` 也是按伤害扣的，比例与 LIF 不同 |

### 结论

**`hitDef.damage` 是唯一决定"这一下掉多少血"的参数**，掉血量与它**精确相等**（不是按比例、
不是受 `atk` 加成影响——本实验里 `ATK: 100` 未变）。
另外，集气量与红血池都随伤害联动，**这是 P10（平衡）必须纳入模型的三个联动量**。

## 5. E3 — 动画时序控制招式快慢

| 项 | 内容 |
| --- | --- |
| **修改前** | Action 200 的首个元素持续 **2** 帧 |
| **修改文件** | `game/chars/p1_kfm_zss_lab/kfm.air` |
| **修改位置** | 第 413 行，`[Begin Action 200]` 的第 1 个帧行 |
| **修改内容** | `200,0, 0,0, 2` → `200,0, 0,0, 20` |
| **预期** | 动画总时长从 12 变 30；`animElem = 3` 的 `hitDef` 触发点相应推迟 |
| **运行方式** | hold `0x09` 1.2 s，burst 抓 37 帧 |

### 实际结果

见 [`montage_e3_mod.png`](evidence/p1/montage_e3_mod.png)。逐帧读 `ElemNo` / `Time`：

| burst | ActionID | ElemNo | Time（元素内/元素总） | 动画累计/总时长 | State |
| --- | --- | --- | --- | --- | --- |
| #02 | 200 | 1/5 | 1/20 | **(2/30)** | 200 |
| #04 | 200 | 1/5 | 5/20 | **(6/30)** | 200 |
| #06 | 200 | 1/5 | 9/20 | **(10/30)** | 200 |
| #08 | 200 | 1/5 | 13/20 | **(14/30)** | 200 |
| #10 | 200 | 1/5 | 17/20 | **(18/30)** | 200 |
| #12 | 200 | **3/5** | 0/4 | **(22/30)** | 200 |
| #16 | 200 | 3/5 | 0/4 | (22/30) | 200（**P2 LIF 已 977**） |
| #22 | 0 | 1/11 | 3/10 | (4/151) | 0（回到待机） |

对照基线（`e4_base_*` 的同一条调试行）：`ElemNo: 3/5; Time: 0/4 (4/12)`。

### 结论

1. **动画总时长 = 各元素帧数之和。** 12 → **30**（`2+1+4+3+2` → `20+1+4+3+2`），
   与覆盖层读到的 `(x/30)` 完全一致。
2. **元素总数不变**（仍 `1/5`）——改的只是首元素的**时长**，不是帧数序列。
3. **`hitDef` 的触发点被推迟。** `hitDef` 挂在 `animElem = 3`（`kfm.zss:224`），
   首元素从 2 帧变 20 帧后，进入元素 3 的时点从第 4 tick 推迟到第 **22** tick，
   即**出招明显变慢、命中判定延后**。这是"用动画时序调招式手感"的直接证据。

> 这一条对 P3/P4/P7 很关键：**招式快慢不需要改逻辑，改 `.air` 的帧数就够。**

| 项 | 内容 |
| --- | --- |
| **修改前** | `Clsn1[0] =  16,-80, 61,-71` |
| **修改文件** | `game/chars/p1_kfm_zss_lab/kfm.air` |

| **修改内容** | `16,-80, 61,-71` → `16,-120, 170,-20`（向右上大幅扩张） |
| **预期** | 攻击框变大；受击框与精灵渲染不受影响 |
| **运行方式** | 先发 `Ctrl+C`（判定框）+ `Ctrl+D`（状态读数），再 hold `0x09` 1.8 s |

### 实际结果

| | 基线 | 改动后 |
| --- | --- | --- |
| 攻击框 `Clsn1`（洋红/红） | 手臂前方一个**细长小矩形** | **巨大红色实心块**，覆盖角色右侧大片区域并被视口裁切 |
| 受击框 `Clsn2`（蓝） | 覆盖角色身体 | **完全相同，一点没变** |
| 精灵渲染 | 正常 | **完全相同** |
| 命中效果 | `P2 LIF 1000 → 977`（Δ23） | `P2 LIF 1000 → 977`（Δ23）**不变** |
| 动画 | `Time: 0/4 (4/12)` | `Time: 0/4 (4/12)` **不变** |

证据对比图：
[`e4_base_clsn_seq02_punchX_burst06.png`](evidence/p1/e4_base_clsn_seq02_punchX_burst06.png) /
[`e4_mod_clsn_seq02_punchX_burst06.png`](evidence/p1/e4_mod_clsn_seq02_punchX_burst06.png)

### 结论

1. **`Clsn1` = 攻击框，`Clsn2` = 受击框**，两者完全独立。
   改攻击框**不会**影响自己的受击框，也不会影响精灵绘制。
2. **判定框与伤害是解耦的两件事。** 本实验把攻击框扩大了几个数量级，
   伤害仍精确是 23（因为 `damage` 没动）。
   **"打得到"和"打多疼"分别由 `.air` 和 `.zss` 控制**——这是 P4/P7 协调打击感的基础。
3. 因此**调整打击范围是一个低风险、可局部化的改动**，不需要碰状态逻辑。

## 7. E5 — 命令路由与优先级

本实验同时验证三件事，是 P1 里信息量最大的一个。

| 项 | 内容 |
| --- | --- |
| **修改前** | `name = "x"` / `command = x` |
| **修改文件** | `game/chars/p1_kfm_zss_lab/kfm.cmd` |
| **修改位置** | 第 291–293 行，`[Command]` 单按钮段 |
| **修改内容** | `command = x` → `command = y` |
| **预期** | 物理 `x` 键不再触发任何招式；物理 `y` 键同时匹配 `name="x"` 与 `name="y"`，按 `command.zss` 的书写顺序，先出现的 `name="x"` 胜出 → 进入 State **200** |
| **运行方式** | 依次 hold `0x27`（前进）、`0x09`（button x）、`0x0D`（button y），各 0.6 s，burst 抓帧 |

### 实际结果 — 基线

见 [`montage_e5_base.png`](evidence/p1/montage_e5_base.png)：

| 输入 | 结果 State | P2 LIF | Δ |
| --- | --- | --- | --- |
| hold 前进 `0x27` | **20**（走路） | 1000 | 0 |
| hold `0x09`（button x） | **200**（站立轻拳） | 1000 → **977** | **23**（= State 200 的 `damage: 23`） |
| hold `0x0D`（button y） | **210**（站立重拳） | 977 → **920** | **57**（= State 210 的 `damage: 57`） |

### 实际结果 — 改动后

见 [`montage_e5_mod.png`](evidence/p1/montage_e5_mod.png)：

| 输入 | 结果 State | P2 LIF | Δ |
| --- | --- | --- | --- |
| hold 前进 `0x27` | **20**（走路，不受影响） | 1000 | 0 |
| hold `0x09`（button x） | **0**（**完全没反应**，`Time` 一路 61→77 在待机） | 1000 | **0** |
| hold `0x0D`（button y） | **200**（站立轻拳，**不是 210**） | 1000 → **977** | **23** |

### 结论

三点全部命中预期：

1. **`.cmd` 定义"物理按键 → 命令名"，是唯一入口。** 把 `name="x"` 的 `command` 改成 `y`
   之后，物理 `x` 键失去了所有对应命令，**任何招式都出不来**（State 恒为 0）。
2. **命令重路由可被精确预测。** 物理 `y` 键同时满足 `name="x"`（新绑定）与 `name="y"`（原有），
   而 `command.zss` 里 Stand Light Punch 的路由（第 239 行）写在 Standing Strong Punch（第 247 行）
   **之前**，所以**先进 200**。这直接印证了 `command.zss:37-41` 的原文规定：
   子集命令必须写在超集之后，否则永远轮不到。
3. **优先级即书写顺序，没有例外。** 这是 E6 在 AI 侧看到的同一规律在命令侧的镜像。

| #04 | **1400** | **0** | 必杀收尾，**KO 对手** |
| #05 | 0 | 0 | 回到待机 |
| #06–#07 | **181** | 0 | Win pose |
| #08 | 0 | 0 | — |
| #09 | **100** | 928 | 新一局，前跑 |
| #10 | **800** | 880 | 投技 |
| #11 | **440** | 754 | 下蹲重脚 |
| #12 | **50** | 722 | 跳跃 |

**用到 7 种不同状态（440 / 810 / 50 / 1400 / 0 / 181 / 100 / 800），第 4 个采样点就把对手 KO。**
这是"正常、多样、有效"的 AI 行为基线。

### 实际结果 — 插入链首规则后

见 [`montage_e6_prio.png`](evidence/p1/montage_e6_prio.png)：

| burst | P1 State | P2 LIF | P1 POW |
| --- | --- | --- | --- |
| #01 | **210** | 1000 | 630 |
| #02 | **210** | 1000 | 780 |
| #03 | **210** | 1000 | 930 |
| #04 | 0（切换瞬间） | 1000 | 1080 |
| #05–#12 | **210**（共 11/12 帧） | **1000** | 1260 → 2310 |

### 结论

1. **AI 直接 `changeState`，不走命令系统。** 本实验里 `.cmd` 是原样未改的，
   而 AI 依然正常出招——进一步印证 E5 的结论。
2. **AI 的优先级 = 源码书写顺序。** 链首那条无条件宽条件规则**夺走了几乎全部决策**：
   状态从"7 种多样"塌缩为"12 帧中 11 帧是 210"。
3. **塌缩的代价是 AI 变哑。** 因为 `210` 的攻击距离不足，AI 在远处反复空挥，
   **对手体力全程 1000 未掉**，自己却把气槽从 630 空挥到 2310。
   这正是"一条写得太靠前的规则会无声废掉后面所有规则"的实例。

> **P8（CPU AI v1）的一等设计对象就是这张顺序表**，
> 并且必须建立"改了顺序之后 AI 行为没有塌缩"的回归检查。

## 9. 横向结论汇总

| # | 实验 | 改什么 | 观测到什么 | 证据类型 |
| --- | --- | --- | --- | --- |
| E0 | 按键通道 | — | 只有 TAB/RETURN 可达引擎 | 状态读数（有/无反应） |
| E1 | `.const` 常量 | `walk.fwd 2.4 → 12.0` | 移动显著变快，位移被推挤盒截断 | 截图 + 位置读数（**倍率未直接读出**） |
| E2 | `hitDef.damage` | `23 → 137` | 掉血 **精确 23 → 137**；集气/红血联动 | 数值读数（精确） |
| E3 | `.air` 帧时长 | 首元素 `2 → 20` | 动画总时长 **12 → 30**，`hitDef` 触发点 **4 → 22** tick | 数值读数（精确） |
| E4 | `.air` 判定框 | `Clsn1[0] 16,-80,61,-71 → 16,-120,170,-20` | 攻击框巨大化；**受击框/精灵/伤害全不变** | 对比截图 + 数值 |
| E5 | `.cmd` + `command.zss` | `name="x"` 的 `command = x → y` | x 键失效；y 键改入 State 200（顺序优先级胜出） | 数值读数（精确） |
| E6 | `AI.zss` 顺序 | 链首插一条 `changeState 210` | 12 帧中 11 帧为 210；**对手全程未掉血** | 数值读数（精确） |

### 三条贯穿性结论

1. **整条执行链（输入 → 命令 → 路由 → 状态 → 判定框 → 受击）全程可在角色文件内验证，
   没有一处需要改引擎。** 引擎 submodule 在 P1 期间保持字节级干净。
2. **"改什么 → 变什么"是可预测、可精确复现的。** E2 的伤害、E3 的时长、E5 的状态号
   都是**精确命中**预期数值，不是"看起来变了"。
3. **两个隐式的优先级系统统治着行为**：命令路由的顺序（E5）、AI 规则顺序（E6）。
   两者都是"先出现者胜"，都会因排序失误而**静默失效**。这是后续阶段最容易踩的坑。

## 10. 已知限制

| 限制 | 影响 | 改进方向 |
| --- | --- | --- |
| 合成输入通道只有 TAB / RETURN 可达 | 无法在一次运行里同时测多个按键；组合键（`x+y`）无法注入 | 寻找更可靠的注入方式（如引擎侧加调试入口），或改用原生手柄模拟 |
| E1 未直接读出速度倍率 | 只证明了常量生效，未读出 5× | P2 用 `displayToClipboard` 输出 `pos x`，改测 time-to-contact |
| 调试覆盖层不输出世界坐标 `pos x` | E1 类"位置/位移"实验只能靠截图目视 | 同上 |
| 状态读数是**抽样**而非逐 tick | burst 间隔内可能漏掉瞬态状态（例如 E6 的 State 0） | 提高 burst 频率，或改用引擎 `printToConsole` 落日志 |
| 未验证判定框的**实际生效边界** | E4 只证明框变大、伤害不变；没有验证"框大到什么程度算命中" | 增加"只扩大攻击框到刚好够到对手"的定量实验 |
| 全部实验依赖本机运行时键位设置 | 他人复现需自行对齐 `save/config.ini` | 在 `tests/p1/README.md` 中明确记录（已记 §2.3） |
