## 0. 术语：什么是「画面知识」

同一个动作在不同作者手里，**只有两类东西是可复用的**：

| 类别 | 例子 | 能否从 kuri 搬 |
| --- | --- | --- |
| **画面知识**（与美术强绑定） | 每帧攻击框/受击框坐标、每帧该显示多少 tick、轴心偏移、每招配哪个音效、投射物从哪射出 | ✅ **能，且应该搬** |
| **战斗框架**（与设计强绑定） | 状态编号、取消链规则、气量经济、硬直约定、AI、跳跃弧线 | ❌ 不搬，见 §1 |

**判定标准**：这个数值只对"这套画"成立 → 搬；这个数值对"这个游戏"成立 → 我们自己定。

## 3. 施工阶段

### 阶段一：攻击框转移（本版执行）

**3.1 提取**
从 kuri `.air` 取出每个动作的逐帧 `Clsn1` 组，得到 `[(活动帧起止, [框...]), ...]`。

**3.2 形状匹配（自动选 kuri 动作）**
对每个我方动作：
1. 量出**高清素材**该动作的武器伸展（超出待机体盒的像素包围盒 → 世界单位）
2. 在候选里选"框的包围盒与该伸展最接近"的 kuri 动作
3. 记录匹配误差；误差过大的**列进报告**，不静默采用

**3.3 转移**
设 kuri 该动作的框外缘 = `K_max`，高清素材实测外缘 = `A_max`：
```
比例 s = A_max / K_max
新框 = kuri 的框 × s × (1/0.48)
```
- ×s：让作者调好的**形状**贴合我们这套画的实际伸展（不照搬他会偏长的距离）
- ×(1/0.48)：抵消引擎 `updateClsnScale()` 的缩放（见 §4）

**3.4 落位**
按 kuri 的"活动帧在原动画中的比例位置"，把框铺到我们重写后的帧序列上。

**3.5 验收**
`airtool validate` 0 错误 0 警告 → 引擎实载 0 崩溃 → 逐招实测触发 → 负责人试玩。

### 阶段二：时序核对（部分已做）

现状：我们的帧序列已按**高清素材自己的节奏**（同源动画）等比分配，总时长保持我们的平衡数据。
kuri 的时序是给**他那套帧数**的，直接搬会与我们的帧数不匹配。

**决策：不搬 kuri 的 tick**，理由写进文档（同源动画的原始节奏优于跨作者搬运）。
仅做一件事：核对各招总时长与 kuri 的差距，超过 ±30% 的列出来人工裁决。

### 阶段三：音效转移（独立，可并行）

## 4. 必须遵守的两条硬规则（来自踩坑）

### 4.1 判定框必须预除以角色缩放

引擎 `char.go:updateClsnScale()`：
```go
c.clsnBaseScale = [2]float32{c.size.xscale, c.size.yscale}
c.clsnScale = clsnBaseScale * clsnScaleMul * animlocalscl
```
→ **AIR 里所有 `Clsn1/Clsn2` 数值运行时都会乘 `size.xscale`**。
我们 `xscale = 0.48`，所以 AIR 里要写「世界尺寸 × (1/0.48)」。
`[Size]` 的推挤盒（ground/air back/front）同理。

### 4.2 投射物 offset **不**跟随缩放

实测确认：`projectile{ offset: 84,-95 }` 按世界尺寸写即正确。
两类数值走不同代码路径，**不要想当然认为一致**。

| 风险 | 对策 |
